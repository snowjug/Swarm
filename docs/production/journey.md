# The critical journey and its failure cases, end to end

This is the integrating test of the production-v1 wave: **one person, one browser, the whole product**. It starts at the
sign-in page and ends at an exported Decision Canvas, in eighteen named steps, and then it breaks things on purpose: a bad
address, a private address, a redirect to the metadata service, a page that never answers, a refusal by the model's safety
filter, a model that is down, a database that is down, a research or a simulation that is cancelled in the middle, a page
that gives orders to an AI, and a second tenant that looks for the first one's project.

It is a test of behaviour, not a demonstration. A step that cannot fail proves nothing, so every assertion in it is one that a
named regression would break (the table below says which), and what is on the screen is looked at as well as asserted:
the screenshots of a run are kept for a person to read.

|               |                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------ |
| Journey       | `e2e/journey/production-journey.spec.ts` (flow A twice, flow B twice)                      |
| Failure cases | `e2e/journey/failure-cases.spec.ts` (fourteen cases, fifteen tests)                        |
| Harness       | `backend/test/support/journey-server.ts` and `journey-{protocol,web,idp,capture,brain}.ts` |
| Helpers       | `e2e/support/journey{,-api,-ui,-hash}.ts`                                                  |
| Configuration | `playwright.journey.config.ts` (the `production` suite)                                    |

## Running it

```sh
npm run build:frontend                      # the harness serves the built page: frontend/dist is needed once
SWARM_JOURNEY_SUITE=production npx playwright test --config playwright.journey.config.ts
```

That starts the harness itself (`node --import tsx backend/test/support/journey-server.ts`), waits for it, and runs the two
specs, **one worker**, in about fifteen minutes on a shared four-core machine (the journey 1.5 to 2.5 minutes a variant,
the failure cases ten or so). Pass a name to run part of it: `… production-journey -g "A-foundry"`,
`… failure-cases -g "failure cases (3|4) ·"`.

**Last full run: 2026-11-04, on the integrated resumed-wave tree (SQLite harness, one worker): 19 of 19 passed in about
nine minutes** (the four journey variants, including the ten-item Decision Canvas and the question-only flow B, and the
fourteen failure cases). The first full run of that tree failed one test: case 9 read the audit log through the database
that it had cut off, so its check that the driver's words are in no log line, span, metric or audit row could never run; it
is made after the database is back. Against a deployed address it has **never** been run.

| Setting                          | Meaning                                                                                                     |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `SWARM_JOURNEY_SUITE=production` | Selects this suite. Without it `playwright.journey.config.ts` runs the demonstration journey it always ran. |
| `JOURNEY_SHOTS=<folder>`         | Where the screenshots go (default `test-results/journey-shots`).                                            |
| `JOURNEY_DB=pglite`              | Runs the harness on PostgreSQL in the process (PGlite) instead of a SQLite file.                            |
| `JOURNEY_PORT_<NAME>=<n>`        | `CONTROL` 3501, `IDP` 3502, `WEB` 3503, `RULES` 3511, `FOUNDRY` 3512.                                       |
| `JOURNEY_TRACE_CRAWL=1`          | Says on stderr how long each short wait of the crawler took (see J-03).                                     |
| `SWARM_JOURNEY_URL`, …           | Runs the specs against a deployed endpoint: see [Deployed-URL mode](#deployed-url-mode).                    |

The harness leaves its data in `data/journey/` (git-ignored) and nothing else on the machine. To read what it captured after a
run, start it by hand (`JOURNEY_DATA_DIR=data/journey-explore node --import tsx backend/test/support/journey-server.ts`) and
point a config at it; `GET http://127.0.0.1:3501/__journey/state` says what is replaced.

## What is real, and what is replaced

The principle: **replace the world, never the product.** Every check that the product makes of its own accord is made. A
test that switched one off would prove nothing about it.

| Real                                                                                                               | Replaced, and how                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The application (`buildApp`), router, guard, rate limits, audit log, job queue                                     | **Microsoft Entra**: `journey-idp.ts`, a loopback identity provider that mints really signed ID tokens (the `oidc` and `tokenVerifier` options). The sign-in itself is real: Authorization Code with PKCE, state, nonce, the session cookie.                                                             |
| The crawler, the fetcher, its address policy, robots.txt, redirects, limits                                        | **The public web and its name lookup**: `journey-web.ts`, a table of names and a connection that ends on this machine, by wrapping `http.request` and `https.request` in the harness process only. A connection to any other host is recorded and fails.                                                 |
| The extractor, ledger, conflicts, participants, constraints, simulation, analysis, critics, brief, decision canvas | **Microsoft Foundry**: `fake-foundry.ts` through the loopback seam the models workstream built (`FOUNDRY_TEST_ALLOW_LOOPBACK`). It checks every reply against the strict schema it was asked for. `journey-brain.ts` answers as a model would; it says nothing about how a real one does.                |
| The database (SQLite in a file; PostgreSQL in the process with `JOURNEY_DB=pglite`)                                | **The search provider** (instance `foundry` only): `ScriptedSearch`, a **test double**. No real provider exists; with none, the product's own default runs (instance `rules`).                                                                                                                           |
| The built page, in a real Chromium                                                                                 | **Timing**: the crawler's timeouts are shortened (the `research.crawl.tuning` option) and the pause between two simulated runs can be lengthened (`analysis.yieldNow`), so that a person can cancel one in the middle. The pause between two requests to one site is the least the configuration allows. |
|                                                                                                                    | **Telemetry and logs**: held in memory (`journey-capture.ts`) instead of being exported, so that they can be read and scanned.                                                                                                                                                                           |
|                                                                                                                    | **A database outage**: a control makes every use of the repository's database throw, as an outage does, and lets it work again.                                                                                                                                                                          |

No seam was added to the product, and no product file was changed. The only edit outside the files this workstream owns is one
line in `playwright.config.ts`: the `journey` project there now ignores the two new specs (which belong to
`playwright.journey.config.ts`), so that running the repository's own suite does not start them.

### The control surface

`/__journey/*` is a **second server on a loopback port** (3501), in the harness process, and **not a route of the
application**: nothing in a deployment has it, and the application cannot be asked to open it. It starts failures and reads
what was captured.

| Route                                                                        | What it does                                                                                                                                                     |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /state`, `POST /reset`                                                  | What is replaced; a clean slate (telemetry, web log, holds, Foundry, search, tuning, pace, outages).                                                             |
| `POST /idp/next`, `GET /idp/visits`                                          | Who the next sign-in is (`analyst` of tenant A, `outsider` of tenant B, or a refusal); what the identity provider was asked.                                     |
| `GET /web`, `POST /web/{reset,hold,release,slow}`                            | Every connection attempted and every request answered; hold a page until released; slow the `/slow/` pages.                                                      |
| `POST /crawl/tuning`, `POST /analysis/pace`                                  | Shorten the crawler's limits; lengthen the pause between simulated runs.                                                                                         |
| `GET /foundry/{requests,problems}`, `POST /foundry/{behaviour,script}`       | What the model was asked (task, schema, status, whether a secret or a page's orders were in it); `natural`, `down`, `content-filter`, `invalid-json`, `refusal`. |
| `POST /search/script`, `GET /search/questions`                               | What the search double offers, or fails with; what it was asked.                                                                                                 |
| `POST /database/outage`                                                      | Takes a database away and gives it back, by instance.                                                                                                            |
| `GET /telemetry`, `POST /telemetry/reset`, `GET /audit`, `GET /audit/verify` | Spans, metrics (cumulative), log lines; the audit log and its chain.                                                                                             |
| `GET /canaries`, `GET /canaries/scan`                                        | The canary strings, and where each was found.                                                                                                                    |

### Canaries

A canary is a distinctive string planted where a secret or private content would be, and then looked for **everywhere
captured**: every log line, span, metric and audit row. They may be found where the person put them (the question, the evidence
they own); nowhere else.

| Canary                                | Planted in                                                                       |
| ------------------------------------- | -------------------------------------------------------------------------------- |
| question                              | the question the person types (`journey-canary-question-…`)                      |
| page                                  | the body of a fixture page (`How the board reviewed…`), so it is in the evidence |
| request header                        | a header that every request of the browser carries                               |
| response header                       | a header that every page of the fixture web answers with                         |
| environment                           | the environment of the harness process, as a secret in a deployment's settings   |
| client secret, model key, model token | the application's own settings, and the fake Foundry's credentials               |

## The people, the instances and the pages

- `analyst` (tenant A) and `outsider` (tenant B) sign in through the identity provider; both hold `Swarm.User` and `Swarm.Admin`
  and each owns a workspace of their own.
- Instance `rules` (3511) has no model and the search that ships (none). Instance `foundry` (3512) has the model path, and the
  search double. Both are the real application over the same built page.
- The fixture web has two sites (`harbour-authority.example.org`, `ferry-operators.example.net`) and, between them: a page
  that is the primary source, a review, a press piece, two pages that **disagree** about a fee (3.40 against 3.90), a page
  that **repeats** another under a second address, a page behind a login, a page that robots.txt closes, a page that does not
  exist, a **slow** page, a page that **gives orders to an AI** among what it says and one that is nothing else, redirects to
  the metadata service, to a loopback address, to a name that resolves privately and from https to http, and a page that
  never answers. Names resolve privately for `intranet-wiki`, `mixed-answers` (a public and a link-local address) and
  `rebinding`. Nothing in them is true of anything.

## The journey

Run for four variants. **Flow A**: the person names a page; **flow B**: the person names none. Each with **rules alone** and
with **a model** (the fake Foundry, scripted as a model would answer), as the matrix says:

| Variant      | Instance | Engine         | What is different                                                                                                                                                                                                                             |
| ------------ | -------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `A-rules`    | rules    | Local rules    | The whole journey, eighteen steps.                                                                                                                                                                                                            |
| `A-foundry`  | foundry  | Model assisted | The whole journey, with the model asked for the scenario, the research plan, the ontology and graph of the sources, the participants, the key actors, the constraints and the critic: each under its strict schema, 8 requests, none refused. |
| `B-provider` | foundry  | Local rules    | A question alone; the search **double** offers six addresses (two pages, and a metadata address, one with a user name, a port, a `file://`); the model is configured and **must not be asked**.                                               |
| `B-default`  | rules    | Local rules    | A question alone, with the real default (no provider): the run ends `blocked`, searches nothing, fetches nothing; the person pastes a note and goes on.                                                                                       |

## Deployed-URL mode

**Implemented and documented. Not run: this environment has no Azure and no network beyond loopback.** What follows is how it is
meant to be run, and what it does and does not do.

```sh
SWARM_JOURNEY_URL=https://<endpoint> \
SWARM_JOURNEY_STORAGE_STATE=<file> \
SWARM_JOURNEY_SITE=https://<a public page that may be read> \
npx playwright test --config playwright.journey.config.ts production-journey
```

- **Signing in** is done once, by a person, in a real browser: `npx playwright codegen --save-storage=<file> https://<endpoint>`,
  sign in with Microsoft Entra, close. The file holds the session cookie: it is a credential, keep it outside the repository
  and delete it afterwards. The spec does not drive the Entra page.
- `SWARM_JOURNEY_SITE` is a public page that the deployed server may read (the person names it, as in flow A);
  `SWARM_JOURNEY_QUESTION` replaces the question; `SWARM_JOURNEY_ENGINE=model` runs the variant with a model, for a deployment that
  has one (the default is rules).
- **Skipped, with the reason written into the report** (`needs the harness`): the failure cases (all of them need a fake), flow B,
  and every step or sub-step that needs the fixture web, the fake Foundry or the capture: 4b, 5b, 6b, 7b, 13b, 14b, 17, 17b, 18.
  What is left is the journey with whatever the deployment has: the sign-in is the person's already, the page named is real, and
  every assertion about the product's behaviour that does not depend on a fixture runs.
- **Steps 17 and 18 are read in Application Insights**, by hand. The run adds an annotation with its start time. Replace
  `<start>` with it:

```kusto
// 17: requests and traces appear, and so do the product's signals
requests   | where timestamp > datetime(<start>) | summarize count() by name, resultCode | order by count_ desc
traces     | where timestamp > datetime(<start>) and message has "request completed" | take 20
customMetrics
| where timestamp > datetime(<start>) and name startswith "swarm."
| summarize points = count(), total = sum(valueSum) by name | order by name asc
// expected from a rules journey: swarm.http.server.duration, swarm.research.{runs,pages,crawl.duration,sources.used,
// evidence.passages,quarantines}, swarm.report.duration; with a model also swarm.model.calls, swarm.model.tokens.
// and swarm.actors.*, swarm.constraints.*, swarm.sim.duration; with a model also swarm.model.task.duration, once for each task.

// 18: nothing private anywhere. The canaries are in the spec's header (journey-protocol.ts): the question, the header.
search "journey-canary-" | where timestamp > datetime(<start>) | summarize count() by $table
// The question's canary may be found only where a person's own text is stored: not in requests, traces, customMetrics,
// customEvents, exceptions or dependencies. The result must be empty for every table.
```

- The window and the canary strings are the only inputs; **a canary found in any table is a defect** (privacy-telemetry.md).

## What the harness does not cover

The fake Foundry says nothing about how a real model replies, its latency, its filters or its price; the web and its name
lookup are a table, so nothing here says how a real site, a real resolver or a real TLS handshake behaves; there is no real
Entra, so conditional access, consent and token lifetime are untested; the browser is Chromium only; telemetry is
captured in the process and never goes through the Azure Monitor exporter; the database is one process, so nothing is
learned of a failover. The deployed-URL mode is meant to close the first and last of those, and has not been run.
