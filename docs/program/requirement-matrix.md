# Requirement matrix: the enterprise-hardening program

Covers the requirements of this program only: the evidence layer, identity, evaluation, demonstrations
and the documents around them. The earlier, much larger matrix for the original build is
[requirements-matrix.md](../requirements-matrix.md); it is not repeated here.

**Statuses.** VERIFIED needs executable evidence named in the row. PARTIAL says what is missing.
NOT BUILT means it does not exist. BLOCKED needs something outside the repository (a credential, a
tenant administrator, an approval). REVIEW means only a person with standing can pass it, and it is
never marked VERIFIED here.

## Changes to a threshold or a test, and why

Nothing was skipped or deleted to make a gate pass. Two changes deserve a reader's attention:

1. **The development-split abstention floor was lowered from 0.55 to 0.40.** The harness had shown the
   gate the sources only; the product also shows it the report, graph and activity of the run. Measured
   as the product runs it, recall on that split is 43%, not 57%. The test that said every off-topic
   question is refused now names the one that is not ("What will the weather be like next Tuesday?")
   and fails if another joins the list or that one leaves it. See
   [ADR 0004](../adr/0004-evaluation-approach.md).
2. **The minimum retrieval score for the gate was lowered from 0.12 to 0.10**, chosen on the
   development split to leave a margin (the lowest answerable score there is 0.13). The reason is in
   a comment beside the constant.

## Defects found by an independent review after these documents were written

After the pitch package was written, a read-only code review of this branch (by a separate reviewer
agent, not the author) found four defects. Each was reproduced first by a test that failed on the
code as it was, then fixed, and the test now passes. None of them was visible to the author's own
tests, which is the point of recording them: the author's review of the branch missed them, and the
same can be true of what the author did not think to look for.

| #   | Defect                                                                                                                                                                                                                                                                                      | Severity | Fix and test                                                                                                                                                                                                        |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `GET /api/projects/:id/compare?with=` loaded the second experiment without a tenant check. A reader in one tenant who knew another tenant's experiment id received its name, seed, status, intervention and per-round metrics (HTTP 200, reproduced), and could tell which ids exist.       | High     | `ownerInTenant` applied to `with`, sharing the guard's 404. `auth.test.ts` "comparing two experiments" (cross-tenant answered as a missing id, in both directions; same-tenant comparison still works).             |
| 2   | Restart recovery walked only the newest 100 experiments across all tenants. The limit became per tenant, so a database can hold more, and an older interrupted run stayed "running" for ever: it could not be deleted, cancelled or restarted, and counted against its tenant's allowance.  | Medium   | Recovery now reads every experiment. `repository.test.ts` creates 200 interrupted runs (100 per tenant) and requires every one to be recovered; 100 were left before the fix.                                       |
| 3   | The analyst's abstention test was a substring match. A reply that began with the abstention sentence and went on to state uncited figures was accepted, recorded as `abstained`, and skipped both the citation rule and the figure check.                                                   | Medium   | An abstention must be the sentence and nothing else. `evidence-gate.test.ts`: the unit rule, `checkAnswer`, and a chat reply that was refused and re-asked. The interface's description of `abstained` is now true. |
| 4   | Passages overlap by 120 characters and begin mid-word, so a cut fragment of one sentence was compared with the whole sentence, or with another document, and reported as a conflict. A supported statement was downgraded to partly supported, and the same conflict could be listed twice. | Medium   | Only sentences a passage holds whole are compared, and a sentence in the overlap counts once. `contradictions.test.ts`: 600 offsets, five mutations each caught. Evaluation results are unchanged.                  |

What the fixes do **not** do: the guard still vouches only for the path. A tripwire test (`auth.test.ts`) fails the build when a route gains a new identifier field, so the next one has to be looked at, but
it cannot tell whether the handler checked it. And a sentence longer than the overlap that straddles
a cut is no longer compared at all (it was compared as two fragments).

## End-to-end runs on the final tree

Before the review fixes, the whole suite passed in Microsoft Edge: 92 tests, 63 against the local
engine and 29 model-assisted against a fake provider. After them it was run again on a machine that
other processes were keeping at full CPU for the whole run (sampled at 100% before, during and after,
with VS Code, the Copilot runtime and the Node processes of an unrelated project among the busiest).
That run **passed 89 and failed 3**. Each failure was investigated rather than assumed, and one
of them (the accessibility test) does reach code the fixes changed, so it was re-run and not reasoned
away:

| Failed test                                                                               | What the log said                                             | Evidence that it is the machine, not the fixes                                                                                                                                                                                                                                                                                                                                                                                            |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `a11y.spec.ts` axe on each guided stage, 1440×900                                         | Test timeout of 120 s; the page was already on the last stage | Re-run three times at each of two viewports: 6 of 6 passed, taking 18 to 57 s (it took 42 s in the earlier clean run), so under load it can sit close to its limit.                                                                                                                                                                                                                                                                       |
| `errors.spec.ts` hostile requests: foreign origin, **oversized body**, wrong content type | `read ECONNRESET` while posting a 700 KB body                 | Fastify answers 413 and closes the connection while the client is still sending (its own source says so), so a reset is a TCP race. Same upload sent 3,000 times to the baseline build (`2e48a51`) and to this one, alternating, on the same loaded machine: **17.0% reset on the baseline, 17.8% on this build**, 413 otherwise (z = 0.75, no difference). It passed in 2 of 3 re-runs.                                                  |
| `model.spec.ts` mid-run provider failure leaves a checkpoint, then resumes                | `read ECONNRESET` on a polling `GET`                          | The server closes idle connections after 5 s (`keepAliveTimeout: 5_000`, unchanged since the baseline) and a starved client reuses a socket the server has just closed. Reproduced on both builds by stalling the client for 5.6 s and reusing 100 idle connections: resets landed on whichever server was addressed first, **on the baseline in one run (28 of 100) and on this build in another (7 of 100)**. It passed 3 of 3 re-runs. |

The settings and tests involved were identical to the baseline when that table was written, and the
two resets looked like transport behaviour that none of the review fixes touched. The accessibility
test is different: its report stage loads the evidence ledger, whose conflict detector was changed,
so a pass on re-run (6 of 6) was the evidence there, not an argument.

### Follow-up: "the machine" was not the whole story

Calling the two resets "flaky under load" and moving on was the wrong conclusion, and a later
investigation overturned it. Load decided _when_ they appeared; the cause was in the product, and
both are fixed.

| Symptom                                                   | Root cause                                                                                                                                                                                                                                                                              | Evidence                                                                                                                                                 | Fix and regression test                                                                                                                                                                                                                 |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ECONNRESET` posting a body over the limit                | Fastify answered 413 with `connection: close` while the client was still sending, so the kernel reset the connection and the client saw a reset instead of the 413 that says what to change. A client on a loaded machine sends slowly, so it is still sending when the server answers. | A Playwright client posting a 700 KB body: **40 of 150 resets (27%)** before the fix, **0 of 150** after.                                                | An `onRequest` hook in `app.ts` refuses a declared `content-length` over the route's limit and drains the rest, closing only beyond 8 times the limit. `backend/test/connections.test.ts` (3 of its 5 tests fail on the old behaviour). |
| `ECONNRESET` on a `GET` after the client had been stalled | The server closed idle connections after 5 s (`keepAliveTimeout`) while a starved client was about to reuse one: the client and the server raced over a socket the server had just closed.                                                                                              | Stalling the client for 5.6 s and reusing 40 idle connections: **3 of 40 resets**; with the timeout at 65 s, **0 of 40, repeated 7 times**.              | `KEEP_ALIVE_TIMEOUT_MS = 65_000`, above the 60 s idle limit that load balancers and command-line clients apply, so the peer closes first. Covered by the same test file.                                                                |
| Axe test timing out at 120 s                              | The test scanned every guided stage in one test. A whole-page axe scan takes seconds on a quiet machine and tens of seconds on a saturated one.                                                                                                                                         | Per-scan timings under load of 17 to 100 s. In CI the scans are quick: the whole 32-step journey, with its scans, adds about 12 s to a 3.7-minute suite. | One test per stage with its own budget, and a unit and hook timeout of 60 s. This one is environmental: the scan is not slower for any reason in the product.                                                                           |

Two further changes came from the same investigation: the secret scanner now reads every blob through
one `git cat-file --batch` process (identical findings, 28.7 s instead of 499 s; covered by
`backend/test/secret-scan.test.ts`), and `npm run audit:ui` starts its own server and waits for its
health check instead of assuming one is already listening (it had been pointed at another program's
server on the same port and timed out). The lesson recorded here is the one the table above gets
wrong: a test that fails only under load is reporting a race, and the race is a defect until shown
otherwise.
