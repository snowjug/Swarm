# 0008. Browser sign-in with Microsoft Entra, run by the server

Status: Accepted (backend and the page's redirect handling). Tested against a local identity provider
that signs real tokens; **not yet run against a real Entra tenant**, because the app registration it
needs can only be created by a tenant administrator. Builds on
[0005](./0005-identity-roles-and-tenancy.md) (token verification, default-deny routes) and
[0007](./0007-workspace-and-project-membership.md) (membership read on every request).

## Context

[0005](./0005-identity-roles-and-tenancy.md) accepts an Entra access token in the `Authorization`
header, which suits an API client but not a person at a browser. A browser needs a way to get one that
does not leave a token where a script can read it: a single-page app that signs in by itself holds
tokens in memory or in web storage, so a single injected script, in a product whose own threat model
names prompt and content injection as an active risk, could take them. A hosted pilot also needs a
person to be signed out when access is taken away, and must never quietly act as the local user.

## Decision

1. **The server signs the person in, not the page.** Authorization Code flow with PKCE (S256), run by
   the server as the client. The page only follows redirects. The code verifier, the `state` and the
   `nonce` are generated by the server (256 random bits each), kept in the database, and never reach
   the page. `state` and the browser binding are stored as SHA-256 hashes.
2. **One attempt, one browser, ten minutes.** A sign-in is bound to the browser that started it by a
   second, `HttpOnly` cookie, is usable once (it is deleted when the reply arrives, whether or not the
   reply is good), and expires after ten minutes.
3. **Identity only.** The scope is `openid profile`: no API access and no `offline_access`, so no
   refresh token exists. The token endpoint's access token is discarded unread. The ID token is
   verified with the same checks as an access token (signature, issuer from the allow-listed tenant,
   audience = the client id, expiry) plus the `nonce`, compared in constant time. A token that carries
   a `nonce` is refused as a bearer token, so an ID token cannot be presented to the API.
4. **A session is a random 256-bit identifier in a cookie, and only its hash is stored.** The cookie is
   `HttpOnly`, `SameSite=Lax` and, on https, `Secure` and `__Host-` prefixed. It idles out after 30
   minutes and ends 8 hours after sign-in (both configurable, bounded). Nothing from Microsoft is
   stored, logged or sent to the browser.
5. **Changes need a header another site cannot add.** A change made with the cookie must carry
   `X-Swarm-CSRF: 1` and come from an allowed origin; a read needs neither, and no read changes state.
   A bearer token is exempt, because a browser does not send one unasked.
6. **One credential at a time, and never the local user.** If an `Authorization` header is present it is
   the only credential considered, so a bad token is not rescued by a cookie. With neither, the answer
   is `401 SIGN_IN_REQUIRED`. There is no path from "no credentials" to the local user once
   `AUTH_MODE=entra`.
7. **Taking access away is immediate where it matters.** Membership is read on every request
   ([0007](./0007-workspace-and-project-membership.md)), and removing someone from a workspace deletes
   their sessions in the same transaction. Roles carried in the Entra token (platform administrator
   only) are read once, at sign-in, so they last at most until the session ends.
8. **Failures say little.** A sign-in that fails for any reason sends the browser to `/?signin=failed`;
   a person who signed in but holds no Swarm app role is sent to `/?signin=norole`. The reason is logged
   as a short code. A return address after sign-in is a path on this site and nothing else.
9. **Audited.** `session.started` and `session.ended` are in the hash-chained log with the person's
   object id and no token; a change refused for want of the header is recorded as `access.refused`.

## Consequences

- **Sessions live in the application's database,** so this works for one instance. More than one needs
  the shared store that [0006](./0006-postgres-adapter-proposed.md) proposes, or sticky routing.
- **Signing out ends Swarm's session, not the person's Microsoft session.** There is no front-channel
  or back-channel logout, and no Continuous Access Evaluation: a person disabled in Entra keeps their
  session until it ends or an owner removes them from the workspace.
- **A platform administrator whose app role is removed keeps it until their session ends** (at most
  eight hours).
- **A client secret is optional** and read only from the environment or a secret store. A public-client
  registration with PKCE alone is supported; whether a tenant's policy allows that is its own matter.
- **Not built:** a membership screen, groups, a login hint, and an account picker. **Not validated:** a
  real tenant, Conditional Access, multi-factor prompts, or the consent screen.

## Evidence

`backend/test/session.test.ts` drives the whole flow through the real server and a test identity
provider that redeems a code only for the PKCE verifier it was issued against: configuration
validation, the cookie format, the authorize request, success, every refusal (replay, another browser,
an old attempt, an error reply, a failing or garbage token endpoint, a wrong nonce, audience, tenant,
expiry, key or issuer, and an access token presented as an ID token), the session on the API, the
anti-forgery header and origin, idle and absolute expiry, sign-out, revocation by removal, log
redaction with canary values, and a second workspace. `frontend/src/api.test.ts` covers the page's
redirect, its once-per-30-seconds guard and the header. Mutation results are in
[the test guide](../TESTING.md#mutation-checks-on-security-code).
