# Requirements matrix — Swarm Lab

This is the gap analysis of the **entire original master specification** plus the extended checklist from the
follow-up review. It does not ask "does Swarm work?"; it asks "does each requested capability exist, and what
executable evidence says so?".

**Status definitions**

- **VERIFIED** — implemented, and an executable check (test, browser run, measurement, scan) that was actually run
  passed. A stub, mock, placeholder or file that merely exists never qualifies. For documentation deliverables
  VERIFIED means the document exists and its checkable claims were re-checked against the code.
- **PARTIAL** — real behaviour exists, but it is narrower than the requirement, or only verified against a test
  double rather than the real thing. "What remains" says exactly what is missing.
- **MISSING** — not implemented. It could be built locally; it has not been.
- **BLOCKED** — cannot be completed or verified without something external: a credential, a cloud
  subscription/tenant, or an owner decision on architecture.

**Evidence keys** (all re-runnable; commands are in [README.md](../README.md))

| Key       | What it is                                                                                                                |
| --------- | ------------------------------------------------------------------------------------------------------------------------- |
| **BT**    | Backend Vitest: `backend/test/*.test.ts`                                                                                  |
| **FT**    | Frontend Vitest: `frontend/src/**/*.test.ts(x)`                                                                           |
| **E2E-L** | Playwright, deterministic local engine, real Edge/Chromium: `e2e/local/*.spec.ts`                                         |
| **E2E-M** | Playwright, model-assisted path against a **fake** Ollama-protocol provider: `e2e/model/*.spec.ts` (not a live model)     |
| **AUD**   | `scripts/ui-audit.mjs`: screenshots, layout metrics and axe at 1920×1080, 1440×900, 1366×768, 390×844                     |
| **SEC**   | `npm audit`, a regex secret scan of every commit, a static search for dangerous APIs, and `backend/test/security.test.ts` |
| **LOAD**  | `scripts/load-test.mjs`, one run on the development laptop                                                                |
| **CLEAN** | `npm ci` + typecheck + lint + tests + build + E2E from a clean copy of the working tree                                   |
| **CI**    | GitHub Actions workflow `.github/workflows/ci.yml`                                                                        |

Test counts at the time of writing: **BT** 276 tests in 21 files, **FT** 336 tests in 21 files, `scripts/azure`
168 tests in 6 files, **E2E** 74 tests (53 local, 21 model-assisted); see "Test evidence" at the end.

Method: every row counts equally. "Fully verified" is VERIFIED rows divided by all rows. "Weighted" scores
VERIFIED as 1, PARTIAL as 0.5, and MISSING and BLOCKED as 0. The counts were computed from the tables above by a
script, not estimated.

How to read these numbers:

- The original specification (a local-first prototype) is largely complete. Its six PARTIAL rows are narrower than
  asked rather than absent: "agents" are orchestrated stages; retrieval is lexical only; storage is not yet behind
  an interface; logging has no telemetry; prompt-injection resistance is untested against a live model; and
  resource use degrades under write load.
- The extended checklist is mostly production and Azure scope, which was deliberately deferred ("do not connect paid
  Azure resources yet"). Ten of its 50 rows are MISSING or BLOCKED for that reason, so the combined figure is
  **not** a measure of readiness to ship. Since the previous revision, B18 became VERIFIED (deterministic quote
  integrity), and B28, B30 and B31 moved from MISSING/BLOCKED to PARTIAL because the Bicep, the Entra token path
  and the least-privilege role now exist and are tested, but none has run against Azure.
- Equal weighting flatters short documents (the threat model counts as much as Entra ID) and a PARTIAL row whose only
  evidence is a fake provider may deserve less than half credit.
- The largest single risk is an unverified claim rather than a missing feature: the model-assisted path has never run
  against a real model.

## Things this matrix deliberately does not claim

- That the application is secure. See [security-review.md](./security-review.md) for evidence and open risks.
- That model-assisted behaviour is good. It is verified only against scripted doubles and a fake provider.
- That the interface is accessible to people. Automated checks plus keyboard tests are necessary, not sufficient.
- That performance numbers generalise beyond the one machine they were measured on.
